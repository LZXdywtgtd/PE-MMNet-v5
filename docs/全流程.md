## 双循环总览

```
[ 输入需求 ] → [ 询问细化 ] → [ 输出计划 ] ← 规划环（阶段0）
                          ↓
               (计划通过，进入执行环)
                          ↓
          修复/开发代码 → 冒烟测试 → 更新文档 → 原子提交 → 等待授权推送
                ↑                                            ↓
                └──────── 再次回到开发 ←──────────────────────┘
```

| 阶段 | 产出 | 核心规则 |
|------|------|----------|
| 0. 规划 | 计划.md（方案/清单/风险/测试） | 必须澄清5大维度，否则不编码 |
| 1. 开发 | 改动的 .py / .json / .sh | 本地冒烟测试无语法错误 |
| 2. 自检 | 单元测试全过 + `inspect.signature()` 验证公开 API | 测试是开发的一部分，不是可选步骤 |
| 3. 文档 | 改动的 .md | **小范围更新随 code commit；大范围重写单独 docs commit** |
| 4. 提交 | 1 个原子 commit（含代码+小文档） | **不攒 commit，一个改动一个 commit** |
| 5. 推送 | `git push origin main` | **commit 由我做，push 由你决定时机** |

## 各阶段详述

### 阶段0：开发策划（需求 → 计划）

在进入"修复/开发代码"之前，所有新功能、重构或非紧急修复必须先走完本阶段。

#### 0.1 需求输入
- 接收自然语言需求（如："跑 V5A6 训练"、"修复仿真预计算内存"）。
- 记录原始需求，不进行主观猜测。

#### 0.2 询问细化（深度澄清）
必须主动向需求方提出以下 5 大维度的澄清问题：

| 维度 | 核心问题 | 目的 |
|------|----------|------|
| **目标（Why）** | 解决什么痛点？预期效果是什么？ | 对齐价值，避免过度设计 |
| **验收标准（What）** | 如何验证成功？具体指标/行为？ | 定义"完成"的边界 |
| **约束（Where）** | 是否受限于特定设备/环境？是否有性能阈值？ | 限制技术选型范围 |
| **影响范围（Who）** | 涉及哪些现有模块？是否向后兼容？ | 规避回归风险 |
| **优先级（When）** | 是 Hotfix（立刻执行）还是正常迭代？ | 决定是否跳过分阶段 |

> **约定**：提问必须得到明确答复，否则不允许进入"计划"阶段。

#### 0.3 输出技术计划（Plan结束）
产出结构化计划，包含：

1. **方案设计**：核心思路
2. **变更清单**：预计修改的文件列表
3. **风险与回滚**：可能影响哪些旧功能？回滚方案是什么？
4. **测试策略**：如何验证（单元测试 / Smoke Test / 手动跑一次完整训练）？

> **注**：v5-α 不使用 PR 流程，计划确认后**直接在当前分支（main）上开发**。

### 阶段3：更新文档

**核心原则**：不追加、整体重写（按用户约定），**小范围文档更新合并入 code commit，只有大范围文档重写才单独 docs commit**。

具体执行：

1. **小范围改动**（如新增 flag 描述、修改函数注释）→ 直接在代码提交时一并提交，**不**单独创建 docs commit。
2. **大范围重写**（如一次性写 8 篇文档）→ 单独执行一次 `docs:` commit。
3. 每次进入本阶段时，检查 [docs/v5_已知问题.md](v5_已知问题.md)：
   - 是否有 bug 被修复（更新状态从"已知"→"已修复"，注明 commit hash）
   - 是否有新 bug（按相同 schema 追加）
4. 重写或新建 active 文档（具体清单见下方文档地图）。
5. **v5-α 不再做 `archived/` 归档**（用户 2026-08-24 反馈："老的不要了，重新写"）。
   - 旧内容直接覆盖，不保留回滚快照。
   - 继承关系在新文档顶部 "继承说明" 段说明。
6. [docs/文档审查指南.md](文档审查指南.md) 在每轮重写时同步更新"## 文档地图"小节。

### 阶段4：原子提交（commit）

**提交粒度**：**每个独立改动一个 commit**（原子提交）。

- 不允许将多个不相关改动攒在一个 commit 中。
- 伴随性的小文档更新（如修改了 CLI 描述）合并入 code commit。
- **只有大范围文档重写**才单独开一个 `docs:` commit。

**Commit message 规范**：

```bash
git commit -m "fix|feat|refactor|docs|perf|chore(<scope>): 简短标题

[背景]  ...（问题或需求背景）
[实现]  ...（做了哪些具体改动）
[修改]  ...（重构、命名等小调整）
[物理修复] ...（物理一致性 bug 修复）
[文档]  ...（文档同步）
[已知问题] ...（未修复但需记录）
[自审计] ...（reuse / simplification / efficiency / altitude 四角度）
[验证]  ...（如何验证）"
```

**前缀规范**：
- `fix:` Bug 修复
- `feat:` 新功能
- `refactor:` 重构（行为不变）
- `docs:` 大范围文档改动
- `perf:` 性能优化
- `chore:` 杂项（配置、脚本）

---

### 阶段5：等待授权推送（push）

**推送节奏**：**一个 commit 推一次**，不要攒多个 commit 一起推。

- **commit 由我做**：本地完成所有 commit 后，主动提示你检查。
- **push 由你决定时机**：你 review commit message 和改动后，授权我执行推送操作。
- 推送命令：
  ```bash
  git push origin main --force
  ```
- v5-α 远程：`git@github.com:LZXdywtgtd/PE-MMNet-v5.git`

**重要产物隔离**（`git add -A` 前必须确认）：
- 永远不入仓：`checkpoints/*.pt`、`logs/*.csv`、`logs/_test_tmp/`、`__pycache__/`
- 使用 `.gitkeep` 保留空目录
- 临时 commit message 文件（如 `.msg.txt`）必须在 commit 前 `git rm --cached` + `git commit --amend` 撤掉

## 循环的边界

| 在循环内（规划环 + 执行环） | 在循环外 |
|---------------------------|----------|
| 所有明确需求的 Bug 修复 | 纯文本 typo 修复（可直接 commit，但需告知） |
| 新特性开发（走完整规划环） | 无代码变动的纯文档维护（如调整排版） |
| 性能优化 + 文档同步 | 跨多周的大型项目（需独立项目文档） |
| 紧急 hotfix（快速走规划环） | 仅由 CI 自动触发的依赖更新 |

### 跑交叉引用检查
```python
import os, re
for root, _, files in os.walk('docs'):
    for f in files:
        if f.endswith('.md'):
            path = os.path.join(root, f)
            with open(path, 'r', encoding='utf-8') as fp:
                content = fp.read()
            for link in re.findall(r'\]\(([^)]+\.md)\)', content):
                base = os.path.dirname(path)
                target = os.path.normpath(os.path.join(base, link))
                if not os.path.exists(target):
                    print(f'BROKEN: {path} -> {link}')
```
